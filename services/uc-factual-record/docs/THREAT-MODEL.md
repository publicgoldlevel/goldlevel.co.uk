# Threat model

## Scope, assets and trust boundaries

Assets are the private dossier, original included document bytes, extracted text, account hashes, session tokens, ingress key, source/build manifests and bounded security logs. The operator, authorized recipients, public internet, existing same-origin website, TLS ingress, container host, CI/repository and private runtime directory are distinct trust zones.

The service is read-only for recipients. Every enabled account can access the complete included dossier. There is no per-team or per-document authorization layer, and separately restricted financial originals are excluded. This is an additional claimant-provided access route, not an official upload service or proof of document receipt/acceptance.

The code repository and image may be visible to others. The private runtime payload must never be committed or served from that public/static boundary. The deployment origin is trusted only after ingress, TLS, Host, header overwrite and loopback routing have been verified.

## Attack, defense and residual risk

| Threat | Defense in the service/package | Residual risk and release condition |
| --- | --- | --- |
| Public evidence exposure through static hosting, Git or image layers | Separate private runtime mount; fixed authenticated routes; source/private-marker checks; no content in the image build. | Review actual repository diff, build context, image layers and ingress/CDN paths. Scans do not prove absence of every secret. |
| Authentication bypass or direct document guessing | Auth before HTML, byte ranges, HEAD, source downloads and text APIs; fixed IDs and default deny. | Run negative tests on every route and live-origin path. A configured login form alone is insufficient. |
| Direct-origin/proxy-header bypass | Secret edge key, exact public Host, forwarded HTTPS check, loopback publication and internal container network. | Host networking/firewall and real ingress overwrite rules must be observed. An exposed host or leaked edge key weakens this boundary. |
| Password guessing, stuffing and account enumeration | Named accounts, salted scrypt, generic errors, dummy hash verification and per-IP/account/global throttles with concurrent-hash cap. | Credential sharing/phishing remain possible. Limits can deny legitimate access and reset on restart. Monitor proportionately; provide access help. |
| Session theft, fixation or stale access | Random server-side rotated sessions; Secure/HttpOnly/Strict cookies; idle/absolute expiry, account expiry checks, logout and restart revocation. | Update the operator-owned account source and redeploy a new installed snapshot to disable an account; restart alone leaves unchanged accounts enabled. Recipient devices and shared-origin compromise remain risks. Downloaded copies cannot be revoked. Single-instance memory storage only. |
| CSRF and login CSRF | Same-origin checks and one-use expiring login proof; session-bound logout proof. No other recipient mutations. | Same-origin XSS can make valid-origin requests. Review the whole origin and keep the mutation surface closed. |
| XSS/content injection | No remote scripts, fixed reader assets, externalized CSP-compatible code, escaping/textContent for text rendering and no runtime template evaluation. | Same-origin scripts elsewhere can read authenticated portal responses. Existing-site audit is a blocking live gate; the portal path is not origin isolation. |
| Root-scoped service-worker interception or persistent cache | No portal service worker; no-store headers and deployment guidance. | Existing workers can intercept and cache despite headers. Inspect browser registrations and deployment code; remove/restrict scope before launch. |
| Cache/CDN/referrer/search disclosure | No-store/private headers, no-referrer, noindex/nofollow/noarchive, no public listing or sitemap registration. | Robots controls are advisory; proxy/service-worker behavior and downloaded copies remain outside application control. Disable CDN caching and test real headers. |
| Path traversal, request smuggling or arbitrary resource retrieval | Reject encoded/ambiguous paths and duplicate security-boundary headers; method/header/body/connection limits; fixed allowlist; no fetch/filepath endpoint. | Upstream parser behavior must agree with the application. Keep proxy/runtime patched and test malformed requests locally and on the owned deployment. |
| Denial of service or resource exhaustion | Request/connection limits, bounded form size, rate counters, pre-auth and hashing caps, container limits and no upload surface. | Internet-scale DoS needs ingress/host capacity controls; global throttling can affect all recipients. No availability guarantee. |
| Malicious or vulnerable original document | Immutable original bytes, authenticated delivery, no server-side PDF parser or execution path. | Hashes do not prove a safe PDF. Use maintained recipient PDF viewers and separately assess source material; do not rewrite original evidence silently. |
| Runtime or supply-chain compromise | Zero npm dependencies, reviewed source, digest-pinned image, constrained container and deliberate update/revalidation. | Node, image/OS, Docker, proxy, host and CI remain dependencies. Unknown vulnerabilities and operator compromise are not eliminated. |
| Secret leakage through logging or GitHub | Runtime secrets outside Git/build; allowlisted audit schema, private-marker check, read-only CI without deploy secrets. | Stable HMAC pseudonyms, opaque document IDs and source hashes remain linkable private metadata. Host/proxy logs and backup practices require review. Do not log requests/bodies/tokens or publish real reproductions. |
| Excess authority, mistaken identity or mistaken receipt claims | Whole-dossier scope documented; offline provisioning; request versus server-response-finish events distinguished from official action. | Credentials can be shared. A finished server response is not proof of client receipt, a full download, reading, consideration, recipient identity, acceptance or official record linkage. |
| Loss of evidence or untested rollback | Source manifests, versioned private imports, known-good image/content pair and backup/restore runbook. | Host restore and custody exercise is pending until performed; code presence is not recovery evidence. |
| Security friction blocks legitimate review | Semantic form labels, ordinary browser/PDF access, text alternatives and planned keyboard/assistive-technology checks. | Target devices, enterprise filtering and assistive tools require reviewer-environment verification; retain an alternative official route. |
| Future AI/prompt-injection/tool exposure | No model, tool, upload, remote retrieval or outbound request capability; startup checks closed policy. | This is a closed capability boundary, not a general AI intrusion detector. Adding AI changes scope and requires new controls and tests. |

## Evidence ladder and scope limits

The package records design, implementation, configuration, test, observation and effectiveness separately. Local synthetic tests can show specific implemented behavior. They do not prove host/TLS/SW configuration, whole-site security, official receipt or continuing effectiveness. The source frameworks and independent reviews are inputs to engineering judgment, not security certification.

Blocking launch gates include private-runtime custody, exact manifest verification, named account provisioning, tested trusted HTTPS ingress, no public origin bypass, whole-origin XSS and service-worker review, target-browser accessibility/PDF checks and a clean backup/restore exercise. Open items remain in `registries/risk-register.json` and `registries/release-gates.json` until supported by dated evidence.

The requested same-origin path is implemented. A separate hostname would provide stronger isolation from existing-site scripts/service workers, but changing the public location is an operator decision outside this package's current route contract. No guarantee of zero-day elimination, complete exploit coverage, ISO certification or full native-framework execution is made.
